# The Factory Floor — Limitations and Opportunities

This document records two things, kept separate from `README.md` (what the system is) and
`CLAUDE.md` (per-session engineering notes): the **real limitations** found while building this
project, and the **opportunities** identified but not built.

Items that were later closed are kept here, struck through and dated, with the original entry
underneath. That is deliberate. A limitation that was found, measured, and then fixed is worth
more as a record than a limitation that was quietly deleted once it stopped being true — and in
several cases the original diagnosis is still correct, it is only the conclusion that changed.

Originally written in Portuguese during the build; translated and brought up to date on
2026-09-04, when the last "still to do" entries had been overtaken by the code.

---

## Known limitations

### 1. ~~Embedding search is unreliable for exact alphanumeric identifiers~~ — RESOLVED 2026-08-25

The diagnosis below is still correct, and the embedding limitation is real and permanent — what
changed is that embeddings stopped being used for this task. A code is not *searched*, it is
**looked up**.

**What was built** (`factory_floor/fault_codes.py`, `CodeAwareRetriever` in `factory_floor/rag.py`):

- Pattern detection of `\b([FA]\d{5})\b` in the operator's message. With no code present, the
  retriever delegates to the usual semantic path — normal questions change in no way at all.
- **Literal** lookup, through Chroma's own full-text filter (`where_document={"$contains": code}`,
  trigram index, so a true substring match). No new dependency and no re-indexing of anything.
- Regex scoring to pick, among all literal occurrences, the one that is actually the
  **definition** — penalising `See also:` / `Note:` before the code and lists of codes, rewarding
  a subsystem prefix (`Power unit:`, `Drive:`, …) right after it. It is the same best-match-per-code
  rule as the 2026-08-18 audit, now in code instead of a throwaway script. It is necessary: the
  first literal occurrence of `F30021` is a useless cross-reference (p.62); the real definition is
  on p.908.
- Exact hits are **pinned to the top** and skip the reranker — an LLM reordering the pool could
  bury the very chunk that defines the code.

**Real measured numbers**, querying with **the code alone, no symptom**, over the 17 verified codes:

| | Contains the code | **Brings the definition page** |
|---|---|---|
| Before (semantic + reranker) | 14/17 (82%) | **3/17 (18%)** |
| After (code-aware) | 17/17 (100%) | **17/17 (100%)** |

The second column is the one that matters: before, even when the code appeared somewhere in the
context, the page that **defines** the fault almost never did.

**The guardrail, which was the most serious risk described below**: zero literal hits is a clean,
unambiguous signal (`F99999` → 0 chunks, verified), and produces an explicit notice at the head of
the context plus rule 1b of `DIAGNOSTIC_SYSTEM_PROMPT`. Verified live: typing just `F99999` returns
*"is not documented in the available manuals… please re-check the fault code on the equipment
display"* instead of describing a different fault. When the code does not exist **and** there is
nothing else in the question, semantic results are suppressed entirely — otherwise the UI would
show "sources" underneath an answer that says it found nothing.

**Typos, handled separately**: `F3OO21` (letter O instead of zero) is not the same thing as a
non-existent code. `difflib` is no use here — not even a 0.75 cutoff links `F3OO21` to `F30021`,
because it sees `O` and `0` as unrelated characters. Normalising the confusions that actually
happen on a display (O↔0, I↔1, S↔5, B↔8, Q, L, Z) resolves it exactly, and the app **asks** the
operator which they meant rather than silently correcting. Guard against false positives: at least
3 genuine digits are required, otherwise words like `FOSSIL` or `BOBBIN` would be caught.

**New artefact**: `fault_codes.csv` — 368 real codes (206 F / 162 A) with file, page and
definition, generated by `build_fault_code_index.py` and committed as static reference data, same
convention as `machines.csv`. Inspectable by hand.

### ~~1 (original entry)~~ Embedding search is unreliable for exact alphanumeric identifiers

Fault codes like `F30021` have no "meaning" of their own to an embedding model — they are labels,
not concepts. Because the List Manual pages all follow the same repetitive structure
(`Power unit: … Cause: … Remedy: …`), a generic question like `"Code F30021"` or `"Fault code
F30021, what should be checked?"` is semantically close to **any** fault-code page, not
specifically the right one. Tested systematically in this project: over ~18 real codes, retrieval
found the right page for only a fraction of them, even at k=15.

The mitigation found (pairing the code with a real symptom, e.g. `"F30021 ground fault"`) works,
but depends on the operator knowing or writing the symptom — it does not solve the case where
someone enters only the code, which is a realistic use case (the code appeared on the equipment
display).

**The associated risk, worse than "it doesn't answer":** because Chroma's retriever always returns
the `k` nearest neighbours (there is no relevance threshold), a question with the wrong code always
retrieves real manual content — just for a different code. The system prompt does not instruct the
model to confirm that the requested code appears literally in the retrieved context before
answering, so the most likely outcome is not "insufficient documentation" but **a well-cited,
grounded-looking answer about the wrong fault**. In industrial maintenance, that can mean applying
the wrong remedy to a real failure.

The industry solution for this class of problem is hybrid search (lexical/exact + semantic),
routing by code-pattern detection, reranking, and a post-retrieval guardrail that validates that
the requested code appears literally in the context before generating — none of which existed in
the project at the time.

### 2. No relevance threshold in retrieval — **tested 2026-08-25, and the test failed for a technical reason**

The problem is still open, but now we know *why* switching the option on is not enough.
LangChain's `similarity_score_threshold` was measured in `notebooks/11_retrieval_benchmark.ipynb`
(axis B) and the result **is not usable**: the Chroma collection was built with
`hnsw.space='l2'`, so LangChain resolves relevance through the Euclidean function, which here
returns values **outside the 0–1 range, some of them negative** (literal warning: *"Relevance
scores must be between 0 and 1"*). With a threshold of 0.2, chunks are discarded regardless of
whether they are relevant — hence 62.2% hit-rate against `similarity`'s 81.1%. **That number
measures a broken metric, not a worse strategy**, and it is recorded that way in the notebook.

Testing this properly would require rebuilding the collection in cosine space
(`hnsw:space="cosine"`), where thresholds mean something. Left as future work, with the path
already identified.

### 2 (original entry). No relevance threshold in retrieval

The retriever always returns 5 chunks, even for questions completely outside the domain (tested:
"what do you think about football" still populates the "Sources retrieved" table). The model
correctly refuses to answer, by prompt instruction, but the UI shows sources that are not really
relevant — which can mislead an operator about what does (or does not) ground the answer.

### 3. ~~No automated test suite / no systematic evaluation~~ — RESOLVED 2026-08-27 → 2026-09-01

Originally: every verification was manual — running notebooks and driving the app live in the
browser. That works as a QA process for one working session, but it does not scale and it does not
protect against silent regressions.

Closed in two halves. **Evaluation** first (item 10 below, 2026-08-21): 37 scored scenarios with a
baseline comparison. Then the **test suite**, in phase 0 of the professionalization work and grown
with every phase after it: **183 tests** (unit + integration) that run with no API key and cost
nothing, plus 3 `llm`-marked tests that do spend money and are deselected by default. `ruff` for
lint, `make test` / `make lint` as the entry points, and GitHub Actions running both on Python 3.12
and 3.13 on every push.

Several of the tests exist specifically to pin down a decision that would otherwise erode —
`test_never_recommends_an_action` (item 5 in the opportunities) fails if anyone adds a
recommendation key to the prior-occurrence summary.

### 4. ~~Maintenance history does not feed the LLM's reasoning~~ — RESOLVED 2026-08-19 → 2026-09-01

Originally: per-machine history was only displayed in the UI (a table), never passed to the model
as context. An operator asking "what do I do about this fault" got no benefit from the fact that
this same machine had already had three similar events — that correlation was left to the human.

Closed in two steps. **2026-08-19**: `factory_floor/agent.py` gives the agent a
`get_maintenance_history()` tool and the model decides when to call it. **2026-09-01**: the
remaining half — the tool read only the static CSV, never the resolutions operators write inside
the app — is limitation **18** below, also closed.

### 5. PDF extraction is text-only — diagrams and nameplates are lost

`PyPDFLoader` extracts running text only. Wiring diagrams, schematics and nameplate photographs —
frequently critical information in industrial maintenance — never enter the searchable corpus.
Still open, and the single most valuable thing the corpus is missing.

### 6. ~~Browser-session state, with no operator identity~~ — RESOLVED 2026-08-28

Originally: Streamlit's `st.session_state` lives per browser session — the app had no notion of
*who* was using it. Two people in the same session saw the same state; the same person in two tabs
had two independent ones. There was no way to know, from the data, who ran a given search or
resolved a given fault.

Closed in phase 5, essentially as opportunity 1 proposed it: `factory_floor/identity.py` signs
operators in against `operators.csv` with PBKDF2-hashed PINs (managed through `manage_operators.py`,
never hand-edited), `FACTORY_FLOOR_REQUIRE_LOGIN` makes sign-in mandatory, and every diagnostic
turn is written to the SQLite audit trail against the operator who ran it. Resolutions an operator
writes carry their name, the timestamp, and the question and answer they were attached to.

The concurrency caveat raised in the original design note was answered by not using a CSV for
writes at all: live resolutions go to SQLite in WAL mode, and `maintenance_history.csv` stays what
it always was — static seed data.

### 7. Corpus still unbalanced between equipment families

~2,766 VFD pages vs ~913 electric-motor pages (~3:1) — already corrected from an initial 18:1
imbalance, but it can still bias retrieval quality slightly in favour of VFDs on ambiguous
"General question" queries with no machine selected. Still open.

### 8. ~~No agent architecture~~ — RESOLVED 2026-08-19 (same day)

The system needed an agentic architecture — a model that autonomously decides which tools to use
and carries memory — not a fixed pipeline. Built the same day: `factory_floor/agent.py`
(`langchain.agents.create_agent`, tools `search_manuals` and `get_maintenance_history`), verified
against 4 real scenarios including a conflict between the described symptom and the photo (the
agent asks for clarification instead of risking a diagnosis). Full detail in `docs/project_log.md`,
section "Session note (2026-08-19, cont.)". Kept here, struck through, as the historical record of
the original gap.

### 9. ~~No tracing / observability~~ — RESOLVED 2026-08-21

Instrumented with LangSmith: `factory_floor/tracing.py` routes every run to a dedicated
`factory-floor` project (without touching the shared `.env`, which points at another project).
`run_diagnostic_agent()` and `ask()` tag and name every call and return a `run_id`;
`tracing.py::run_url()` builds a direct link for either (a custom mechanism was needed, since
`LangChainTracer.get_run_url()` only sees runs created by the callback manager and fails for
`@traceable`-decorated calls such as `ask()`). Verified live in
`notebooks/08_tracing_observability.ipynb`: a real multi-step trace (the agent chose to call
`get_maintenance_history` then `search_manuals`, in that order, on a real F30059 question about
VFD-06), a single-chain baseline trace for contrast, and the zero-tool-call reasoning trace from
the conflicting-signals scenario. Technical details (SDK caching, import order vs `load_dotenv()`)
are in `CLAUDE.md`'s 2026-08-21 note.

### 10. ~~Evaluation never run automatically, with no baseline comparison~~ — RESOLVED 2026-08-21

`eval_scenarios.csv` — 37 troubleshooting scenarios, each with a root cause and a manual evidence
phrase individually verified against the real vector store (the evidence never repeats the
code/symptom already present in the question, so a model cannot score by echoing it).
`factory_floor/evaluation.py` scores `rag.ask()` (baseline) and `run_diagnostic_agent()` (agent)
identically. Real numbers, `notebooks/10_evaluation_baseline.ipynb`:

- Root-cause accuracy: 78.4% agent vs 75.7% baseline. Evidence accuracy: 45.9% vs 48.6% (close —
  an honest echo of limitation #1 above).
- Machine-history awareness: baseline 0% (structural, confirmed by `assert`); the agent correctly
  cited the real history date (2022-06-25).
- Conflict resolution (a `structural_damage` photo plus text downplaying it as "just a cosmetic
  scuff"): the agent asked for clarification; the baseline, with no `vision_context` mechanism at
  all, took the description at face value and concluded it was "likely safe to continue running" —
  a real and slightly worrying finding about the difference between the two architectures.
- Safety audit (see item 11): 12/30 failures for the agent (40.0%) vs 32/34 for the baseline
  (94.1%) — reported exactly as it came out, not tuned until it looked better.

The defect classifier already had this comparison; now the RAG/agent path has it too.

### 11. Safety Data Sheet (SDS) corpus still missing — everything else in this item is closed

The original design called for a mixed corpus — manuals **plus** safety data sheets for the
lubricants, oils and cleaning products used on the equipment — to support the safety-first output
contract.

**What was built instead, and is enough for the contract itself**: rule 6 in
`factory_floor/agent.py::DIAGNOSTIC_SYSTEM_PROMPT` (grounded in the safety sections the motor/VFD
manuals already contain, no SDS needed) and `factory_floor/safety.py` (LLM judge + deterministic
regex cross-check, `notebooks/09_safety_validator.ipynb`). Audited over the full evaluation set in
`notebooks/10_evaluation_baseline.ipynb`: the agent still fails on 40.0% of the answers that
recommend an action (12 of 30) — the rule helps a great deal (the unruled baseline fails 94.1%) but
does not guarantee 100%, confirmed live in the running app.

**Closed since (2026-08-28, phase 4)**: this item used to end with "still missing: a version of the
Safety Validator that blocks or warns in real time in the app; today it is only a post-hoc audit
used in evaluation". That is no longer true. `safety.enforce_safety()` runs as a **live gate**
before the operator ever sees the answer, with three modes — `off` | `rewrite` | `block` —
configured by `FACTORY_FLOOR_SAFETY_GATE_MODE`. A 40% prompt-level failure rate is exactly why it
was worth building.

**What genuinely remains open**: the SDS corpus itself. Without it, precautions are limited to what
the motor/VFD manuals say about general safety, not to product-specific safety sheets for chemicals
and lubricants.

### 12. The defect dataset is not specifically about motors/VFDs

The 4 curated MVTec AD categories (`cable`, `metal_nut`, `screw`, `transistor`) were chosen as
components physically plausible on or around a motor/VFD, but they are **not real photographs of
motor or drive failures** — they are generic parts from an academic anomaly-detection benchmark.
This limits how directly the classifier generalises to the real defects an operator would see
(worn bearings, damaged windings, corroded terminal boxes, dust-clogged VFD heat sinks, damaged
cooling fans, melted or oxidised cable connectors) — none of which appear in the current dataset.
See opportunity 3. Still open.

### 13. The zero-shot vision baseline performs worse than the trivial baseline

Measured, not hypothetical: on the held-out test split, the zero-shot vision model (`gpt-4.1-mini`)
scored 42.5% accuracy — **worse than always predicting "good"** (77.1%, the majority class). The
zero-shot model invents defects even in photographs of undamaged parts (only 7% recall on the
"good" class). It is a real failure-analysis finding, and it confirms that a pure zero-shot
approach is not reliable for this task without a trained classifier behind it.

### 14. ~~Photo action recommendations are not grounded in the manuals~~ — SUPERSEDED 2026-08-19

Originally: `recommend_actions()` generated "what to do" text from the LLM's general knowledge
about the defect type, not from retrieval over the manuals — flagged explicitly in the UI ("Not
grounded…"), but the risk of generic, subtly wrong advice was real.

Superseded rather than fixed in place: when the diagnostic agent was built the same month,
`recommend_actions()` was retired from the main flow. A photo is classified before the agent
reasons, the classification is injected as context, and the agent produces the final
recommendation itself — grounded in whatever tools it chose to call, cited like any other answer.
The function still exists for the notebook, where it is compared against the agent's output.

### 15. Evaluation scoring is a keyword proxy, not human judgement

`factory_floor/evaluation.py::keyword_score()` checks whether a specific phrase appears literally
in the answer — a correct answer worded differently counts as a miss; a wrong answer that happens
to repeat the keywords counts as a hit. The 50% "pass" threshold is arbitrary, chosen once and
never tuned against the results. `source_score()` checks only the manual family (the file name),
not the exact page — there is no human page-level ground truth for these 37 scenarios. Mitigated,
not eliminated: `expected_evidence_keywords` are always confirmed absent from the question itself,
so nothing can score by echo. Still a proxy.

### 16. Self-preference bias in the safety judge

`factory_floor/safety.py::check_safety_precautions()` uses `gpt-4.1-mini` to judge answers
generated by the same `gpt-4.1-mini` — a real risk of self-preference bias. Mitigated with a second
deterministic regex checker (`check_safety_precautions_keyword()`) that makes no LLM call at all;
the agreement rate between the two (91.9% on agent answers, 78.4% on baseline answers, measured
2026-08-21) is published as the honest confidence level in the judge's number rather than hidden.

### 17. LangSmith traces live in an account shared with unrelated projects

`factory_floor/tracing.py` isolates this project's traces in a dedicated LangSmith project
(`factory-floor`), but that is separation at *project* level, not account or organisation — the
same LangSmith account (and the same `LANGSMITH_API_KEY` in the shared `.env`) is used by unrelated
work. The trace URLs printed in `notebooks/08_tracing_observability.ipynb`, and kept in its
committed outputs, contain the organisation/tenant UUID.

Now that the repository is public, that is a fact rather than a caution: three such URLs are in the
committed outputs. They are not credentials and grant no access — anyone opening them without
membership of the organisation sees nothing — and they are evidence that the traces are real, which
is why they are still there. Worth knowing before publishing screenshots from the same account.

### 18. ~~Operator-written resolutions never reached the agent~~ — RESOLVED 2026-09-01 (same day)

Found on 2026-09-01 during manual testing of the app (sign in as one operator, run a diagnosis for
VFD-04 / `F30805`, record the resolution in the machine's history; then sign in as another operator
and ask the same question — the agent was called again, spent money, and completely ignored the
resolution that had just been written).

**Cause.** The "Record what you actually did" button writes operator resolutions to the audit
database (`resolution_events`, via `audit.append_resolution_event`). `machines.get_machine_history()`
knows how to join those live events onto the static CSV — but only with `include_resolutions=True`.
The agent's tool used the default, `include_resolutions=False`. So a resolution an operator wrote
appeared in the UI's "Maintenance history" panel but was **invisible to the agent** on a later
question about the same code on the same machine.

**Deliberate in origin, not a bug.** `include_resolutions=False` was chosen as the default to keep
`notebooks/05_maintenance_history.ipynb` and the agent tool unchanged when history writes were
added in phase 5. A scoping decision — but the practical effect was that the loop "operator
resolves → system records → system uses it next time" stayed open at the last step.

**Fixed the same day:**

- `agent.py::build_history_tool` now calls `get_machine_history(machine_id,
  include_resolutions=True)` — the agent sees operator-written resolutions.
- `format_history()` gained date ordering (oldest first) and a `HISTORY_MAX_ROWS = 20` cap, with an
  explicit note of how many events were omitted: live history grows without limit and would
  otherwise inflate the agent's prompt on every turn.
- `DIAGNOSTIC_SYSTEM_PROMPT` now states that `[operator_resolution]` entries are **unverified field
  notes** — a useful lead, never a documented fact, never citable as manual content, and only to be
  used while declaring where it came from.
- New tests for ordering and truncation in `tests/unit/test_agent_helpers.py`.

This closed the *knowledge* loop (the agent knows), not the *cost* loop — see opportunity 5, which
was built later the same day.

### 19. ~~The safety gate spent money without being counted~~ — RESOLVED 2026-09-01

Found while explaining the breakdown of the LLM calls in a single turn. Phase 3's
`CostTrackingCallback` was attached via `config={"callbacks": [cb]}` **only** to the agent call.
`services.run_diagnostic::_apply_gate` invoked `enforce_safety(...)` with an `llm` carrying no
callback and no config — so the **safety judge** (and, when it failed, the rewrite plus the
re-check: up to 3 calls) was real spend that:

- did not appear in the sidebar's "Session LLM cost" line,
- did not count towards the daily spend cap (`FACTORY_FLOOR_DAILY_SPEND_CAP_USD`) — meaning the cap
  under-counted and could be exceeded without blocking,
- did not appear inside the agent's trace tree in LangSmith (it showed up as a separate run).

**Fix:** `check_safety_precautions()` and `enforce_safety()` now accept an optional `config`
parameter, forwarded to all three `.invoke()` sites (judge, rewrite, re-check);
`services._apply_gate` passes the same `agent_config` used for the agent call. New tests in
`tests/unit/test_safety_gate.py::TestCostConfigForwarding` confirm the config reaches all three
sites and that omitting it is still valid.

### 20. ~~The safety gate never ran outside English~~ — RESOLVED 2026-09-01

The worst bug found in the project, and the one that best explains why the multilingual UI needed
testing in more than one language.

To avoid paying for a judge call on answers that recommend no physical action, the gate takes a
cheap shortcut: if the answer matches no action verb, skip the judge. `_ACTION_VERB_PATTERN`
matched **English verbs only**. So a Portuguese, French, Spanish or German answer never matched,
always took the shortcut, and never reached the judge — the safety gate was effectively **switched
off in four of the app's five languages**, while reporting itself as active.

Found by chasing a user-facing symptom ("why is the Portuguese answer nothing like the English
one?"), not by reading the code. Fixed by restricting the shortcut to English and sending every
other language straight to the judge — a slightly higher cost, in exchange for a gate that is
actually on. The lesson generalises: an optimisation keyed on natural-language pattern matching
silently becomes a feature switch when the language changes.

## Opportunities

### 1. ~~Per-operator authentication, tied to a specific person~~ — BUILT 2026-08-28

Proposed as a simple login associating each session with an identifiable operator, so that the
person responsible for a diagnosis or repair is recorded, can write down inside the app what they
actually did to fix the fault (free text, with date and time), and have that record — operator +
steps + timestamp, linked to the original question and the grounded answer — stored in the
machine's history, turning `maintenance_history.csv` from a static generated file into a living,
writable table.

Built in phase 5, close to the proposal. Two of the three design questions raised were answered
differently, and better:

- **Where writes go.** Not the CSV. Live resolutions go to a separate SQLite table
  (`resolution_events`) in WAL mode, and `machines.get_machine_history()` joins them onto the
  static CSV on read. The distinction the proposal wanted — "events generated by the app" vs
  "original simulated history" — survives in the data, not just in a column.
- **Concurrency.** The race condition the note flagged for concurrent Streamlit sessions writing
  the same CSV never had to be solved, because SQLite/WAL handles it.
- **Authentication.** No `streamlit-authenticator` dependency: `identity.py` verifies PBKDF2 PIN
  hashes from `operators.csv`, and `manage_operators.py` is the only supported way to add an
  operator or change a PIN.

### 2. ~~A button to push the record to other factory systems~~ — BUILT 2026-08-28

Proposed as a single demonstrative button simulating the hand-off of a resolution record
(operator + steps + timestamp + fault) to a CMMS (SAP PM, IBM Maximo) or ERP — the point being to
show the integration seam, not to build the integration.

Built exactly at that scope: "Send to CMMS/ERP (demo)" appends the structured record to
`data/cmms_outbox.jsonl` and confirms with a toast. The file is the seam — in a real deployment
that append becomes an API or webhook call, and nothing else about the flow changes. A second
button, "Email to supervisor", opens a `mailto:` with the record pre-filled: no SMTP server, no
credentials, no background sending.

### 3. More data — photographs representative of real motor and VFD faults

The defect classifier is trained on a generic academic dataset (MVTec AD), curated only by
component analogy (cable, nut, screw, transistor — see limitation 12), not on real failures in this
domain. The highest-impact improvement to the vision path would be assembling a genuinely
representative set: worn or corroded bearings, burnt windings or degraded insulation, corroded
terminal boxes or ones showing signs of overheating, dust-clogged VFD heat sinks, damaged cooling
fans, melted or oxidised cable connectors.

Attempted once and **deliberately abandoned**, which is worth more than the attempt: a candidate
thermal-imaging dataset trained to 98.9%, but its 369 images turned out to be only **11 independent
scenes** of near-identical frames (neighbouring frames differing by 0.55–2.47 grey levels out of
255), with a single scene for three of the four classes — so no split could measure generalisation
at all. The cheap neighbouring-frame test that exposed it is the reusable part.

### 4. Audio — diagnosis from the sound of the motor or drive

Same principle as vision, for sound: the operator records or uploads the noise a motor or drive is
making, the system "listens" and suggests the likely problem plus the checks to run. Investigated
2026-08-19 and deferred: the available dataset needs significant preparation before any training,
and the vision path already covers the multimodal ground.

**A real dataset was identified** (not a generic one, unlike the care MVTec required): the
**UOEMD-VAFCVS** (University of Ottawa Electric Motor Dataset — Vibration and Acoustic Faults under
Constant and Variable Speed Conditions), Mendeley Data, DOI `10.17632/msxs4vj48g`. Recorded from a
real induction motor **driven by a real VFD** on a test bench (SpectraQuest Machinery Fault & Rotor
Dynamics Simulator), with a microphone, 3 accelerometers and temperature. The faults are directly
relevant to this domain: rotor imbalance, misalignment, stator winding faults, voltage imbalance,
bowed rotor, broken rotor bars, bearing faults.

**Why it is not as straightforward as MVTec was:**

- Only 128 recordings in total (8 motors × fault conditions × constant/variable speed), far fewer
  than the 1,502 images used for vision — it will need data augmentation or a few-shot approach,
  not straightforward supervised classification.
- The files are multi-sensor CSVs (accelerometer + audio + temperature columns), 10s at 42 kHz —
  not ready-to-use audio. The acoustic channel has to be extracted, cut into clips, and probably
  turned into spectrograms/MFCCs before any classifier (`librosa` or `torchaudio`, neither of which
  is in the project).
- The labelling scheme (`{Letter}-{Letter}-{Number}-{Number}`, e.g. `H-H` = healthy, `B-B` = faulty
  bearing) needs mapping to readable labels, as was done for vision's `COARSE_LABEL_MAP`.

**When picking this up**: follow the same discipline used for vision — do not assume the dataset's
structure from memory, download and inspect it first, and confirm the real label mapping before
writing any training code.

### 5. ~~A zero-cost shortcut for a case already resolved on this machine~~ — BUILT 2026-09-01 (partial)

Motivated by the same manual test that produced limitation 18. Before the fix, if an operator had
already recorded the resolution for exactly this fault code on this machine, a later question about
the same pair still ran the full agent and still paid for an LLM call.

**Built, but deliberately not as "serve the resolution instead of the diagnosis".** Designing it
against VFD-04's real data, the naive version turned out to be dangerous: `F30805` was answered
twice with "Replaced the power unit module" and **came back anyway**, then three times with a
simple power cycle. A frequency count would recommend the power cycle 3 votes to 2 — that is,
recommend **masking a recurring hardware fault**. Without knowing whether each action *worked*,
"most frequent" is never "most effective".

What was built:

- `factory_floor/recurrence.py` — **no LLM at all**. Only counting, sorting and date arithmetic
  over records that already exist: `code_in_question()`, `find_prior_occurrences()`, `summarize()`,
  `prior_occurrence_report()`. Nothing in the panel can be invented, because nothing is generated.
- **Interception before the diagnosis** (`app.py::submit_turn`, the same pattern as the typo
  confirmation): if the question carries **one** fault code, a machine is selected, it is the first
  question of the conversation, and that code has already occurred on that machine, the panel is
  shown at zero cost and the app waits. The operator chooses between "Run the full diagnosis
  anyway" and "That's enough". With no code, no history, or on a follow-up, the normal diagnosis
  runs without interruption.
- **The panel reports, it does not recommend.** A table of occurrences (date, what was done, by
  whom, outcome, source, downtime hours) plus a recurrence warning with the shortest interval
  between them. A test (`test_never_recommends_an_action`) fails if anyone adds a recommendation
  key to the summary.
- **Two new columns in `resolution_events`** (with an idempotent `ALTER TABLE` migration for
  existing databases): `fault_code` — without it, a recorded resolution was not even *findable* on
  the next occurrence, which was the real blocker — and `outcome`
  (`resolved` | `temporary` | `not_resolved`). The recording UI now asks for both.

**Still open:** `outcome` has only just started being collected, so there is not yet data to rank
actions by effectiveness. After months of use it becomes possible to say "the module replacement
held for 4 years; the reset held for 2 days" — and only then does a history-based recommendation
have any foundation.

### 6. A knob to turn the reranker off

The reranker is the most optional LLM call on the critical path — measured at +5.4pp hit-rate and
+0.075 MRR, for 8s → 45s of latency (limitation table in the README). Every other expensive or
opinionated behaviour in the project is switchable through a `FACTORY_FLOOR_*` setting; this one is
still hard-coded as `rerank=True` in `factory_floor/services.py::build_diagnostic_retriever`.

A deployment that cares more about latency or cost than about ordering has no way to trade one for
the other without editing code. The change is small — a `Settings` field, threaded through the same
call — and the benchmark that justifies either choice already exists.
